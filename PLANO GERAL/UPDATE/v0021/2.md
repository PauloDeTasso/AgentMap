Sim. E com essa nova evidência, eu **mudaria uma parte importante do plano anterior**.

A documentação oficial atual do Kilo confirma exatamente o mecanismo que precisamos: **Custom Subagents são agentes reais do Kilo, com `description`, `mode`, `prompt`, `permission`, modelo etc.; o agente primário pode invocá-los pela `task`, em sessão isolada, e a própria descrição ajuda o Kilo a decidir quando delegar.** ([Kilo][1])

Também confirmei o ponto crítico do **Agent Manager**: a documentação pública atual descreve a tarefa do `agent_manager` com `prompt`, `name` ou `branchName`, e `model`/`variant`, mas **não documenta um campo `agent` para selecionar um Custom Subagent na criação da sessão**. Portanto, não devemos projetar o AgentMap supondo que esse parâmetro exista. ([Kilo][2])

E isso leva a uma arquitetura melhor:

> **AgentMap não deve tentar forçar o Agent Manager a "ser" um agente. Ele deve fazer com que os agentes oficiais do AgentMap sejam registrados como Custom Subagents do Kilo e controlar quando e quais deles podem ser delegados.**

# 14. Permissões

Aqui a documentação é especialmente útil.

O Kilo permite:

```text

  edit:
  bash:
  read:
  task:
```

e inclusive permite controlar **quais subagentes um agente pode chamar** usando `permission.task`. ([Kilo][3])

Então o AgentMap deve gerar isso a partir da política real de cada agente.

Exemplo conceitual:


Isso é muito mais forte que escrever:

```text
"não chame agentes não autorizados"
```

no prompt.

# 16. E o Agent Manager?

Aqui está uma descoberta muito importante.

A documentação atual do Agent Manager diz que ele cria sessões isoladas em worktrees e que o `agent_manager` pode ser chamado pelo chat. Porém, a API documentada da tarefa não mostra um parâmetro `agent`; ela fala em `prompt`, `name` ou `branchName`, além de `model`/`variant`. ([Kilo][2])

Portanto:

### Não farei isto:

```text
agent_manager({
    agent: "backend"
})
```

sem comprovação do schema real.

### Faremos isto:

```text
Task Tool
   ↓
Custom Subagent "backend"
   ↓
sessão isolada
```

quando a execução puder ser tratada como subagente.

E usaremos:

```text
agent_manager
```

para a infraestrutura de worktree/execução quando realmente necessário.

## 🧠 Minha conclusão como arquiteta do AgentMap

Depois dessa confirmação documental, **eu não tentaria "ensinar" o Agent Manager a conhecer os agentes do AgentMap**.

Isso acoplaria o AgentMap a uma implementação específica do runtime.

Eu faria algo melhor:

```text
                 AGENTMAP
                    │
             SOURCE OF TRUTH
                    │
                    ▼
          KiloAgentGeneratorService
                    │
                    ▼
             CUSTOM SUBAGENTS
                    │
                    ▼
                 KILO
                    │
          ┌─────────┴─────────┐
          │                   │
       direto              Task Tool
          │                   │
          │             Custom Subagent
          │                   │
          │             precisa isolamento?
          │                   │
          │              ┌────┴────┐
          │              │         │
          │             não       sim
          │              │         │
          │              ▼         ▼
          │           sessão    Agent Manager
          │                       ↓
          │                    worktree
          │                       │
          └───────────────────────┘
```

**Esse desenho aproveita o que o Kilo já implementa, em vez de lutar contra ele.**

E há uma evidência particularmente forte a favor disso: o próprio Kilo está abandonando o antigo Orchestrator dedicado porque **Code/Plan/Debug já conseguem delegar diretamente usando subagentes**. Portanto, construir um segundo orquestrador paralelo dentro do AgentMap seria caminhar contra a direção atual do produto. ([Kilo][5])

O AgentMap deve ser o **governador/registro/origem das identidades e políticas**; o Kilo deve ser o **runtime inteligente de delegação e execução**; e o Agent Manager deve ser a **infraestrutura de sessões/worktrees**. Essa separação é, para mim, o desenho mais sólido baseado no que está efetivamente disponível hoje.
