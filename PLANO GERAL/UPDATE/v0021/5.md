# Plano — Usar os agentes reais do AgentMap no Agent Manager (com triagem para tarefas pequenas)

**Para mim mesmo, como agente principal operando o AgentMap.** Este plano corrige um comportamento meu que não deveria existir: hoje, quando abro um worktree no Agent Manager, eu invento a identidade de quem vai trabalhar ali em vez de usar os agentes que o próprio AgentMap já tem configurados — com persona, permissões e contexto definidos. Isso não é uma limitação do Kilo, é um cabo solto entre duas peças que já existem no AgentMap e nunca foram conectadas.

Baseado em evidência real: código do repositório `PauloDeTasso/AgentMap` (branch `main`) + documentação oficial do Kilo Code (`kilo.ai/docs/customize/custom-subagents`, `kilo.ai/docs/automate/agent-manager`, `kilo.ai/docs/code-with-ai/agents/model-selection`).

---

## 1. Causa raiz (evidência de código, já confirmada)

A tool `agentmap_abrir_worktree` (`backend/src/mcp-server/tools/worktree.ts:92-198`) monta a instrução que eu recebo assim:
```ts
prompt: `Executar tarefa ${tarefaId}: ${tarefa.titulo}`
```
Só isso. O campo `tarefa.agenteResponsavel` (quem deveria fazer aquilo, segundo o AgentMap) fica guardado numa "intenção" interna (`worktree-intentions.json`) e **nunca chega no texto que eu recebo**. Nada me diz "use o agente Backend configurado, com essa persona, essas permissões, essas regras". Por isso eu invento.

O AgentMap já tem as duas peças que resolveriam isso, só não estão ligadas:
- Registro de agentes reais: `esquemas/agentes-registry.schema.json` e `agente-perfil.schema.json`.
- Serviço que sabe gerar arquivo de agente customizado do Kilo a partir desse registro: `KiloAgentGeneratorService.montarMarkdown()` (`backend/src/servicios/KiloAgentGeneratorService.ts:204-224`), que já produz frontmatter `mode:` e `permission:` — só que hoje é chamado apenas para gerar **contexto de tarefa**, nunca para gerar a **identidade do agente**.

---

## 2. Confirmação contra documentação oficial do Kilo (não suposição)

- **Custom Subagents é recurso real e documentado**: `kilo.ai/docs/customize/custom-subagents`. Definidos via `kilo.jsonc` (bloco `"agent": {...}`) ou arquivo markdown com frontmatter `description`, `mode`, `permission`, seguido do prompt de sistema. Formato **compatível** com o que `KiloAgentGeneratorService` já gera.
- **Seleção automática por descrição já existe no Kilo**: "agentes primários (especialmente o Orchestrator) podem invocar subagentes automaticamente via Task tool quando a descrição do subagente combina com a tarefa em questão". Isso significa que, se os agentes do AgentMap existirem como custom agents de verdade no Kilo (com `description` bem escrita), **o próprio Kilo já sabe evitar chamar um especialista para algo que não precisa** — é o mecanismo nativo que resolve exatamente a sua ressalva.
- **Ponto que não consegui confirmar com 100% de certeza**: se a tool `agent_manager` (usada para abrir worktrees) aceita um campo `agent:` por tarefa para forçar um custom agent específico na sessão nova, ou se isso só se aplica a subagentes invocados via Task tool dentro de uma mesma sessão (mecanismo diferente de abrir um worktree novo). A documentação lista que cada tarefa do `agent_manager` precisa de pelo menos `prompt`, `name` ou `branchName` — não vi `agent` citado explicitamente nessa lista. **Isso precisa ser verificado no meu próprio ambiente** (inspecionar o schema real da tool `agent_manager` que tenho disponível) antes de eu assumir que dá para forçar o agente diretamente por parâmetro. Enquanto isso não for confirmado, a via garantida é referenciar a persona explicitamente dentro do próprio `prompt`.

---

## 3. Regra de triagem — nem toda tarefa precisa de agente especializado + worktree

Isso é a parte que eu preciso respeitar sempre, não é opcional: abrir um worktree tem custo (novo branch, nova sessão, espaço em disco, tempo). Antes de chamar `agentmap_abrir_worktree`, minha decisão deve seguir este critério:

```
A tarefa é pequena, sem risco, e eu já tenho tudo que preciso pra fazer agora mesmo?
  → SIM: eu mesmo faço, sem abrir worktree, sem chamar agente especializado.
  → NÃO (exige domínio específico, mexe em área sensível, é grande o suficiente
    para rodar em paralelo com outra coisa, ou o próprio AgentMap já marcou um
    agenteResponsavel específico e diferente de mim para essa tarefa):
    → abro worktree, e nesse caso USO o agente configurado, nunca invento um.
```

Essa regra já existe implicitamente na tool `agentmap_recomendarAgente` (que hoje eu posso ignorar) — o que muda é que ela passa a ser **consultada por padrão antes de decidir**, não uma opção que eu esqueço de usar.

## 4. Mudanças concretas necessárias

### 4.1 — Backend: gerar a identidade do agente, não só o contexto da tarefa
Em `agentmap_abrir_worktree` (`worktree.ts`), antes de montar `dados.instrucaoAgenteManager`:
1. Buscar o perfil completo do agente pelo `tarefa.agenteResponsavel` no registro (`agentes-registry`/`agente-perfil`).
2. Se o arquivo de custom agent ainda não existir (`.kilo/agent/<agenteId>.md`), chamar `KiloAgentGeneratorService` para gerá-lo a partir desse perfil (persona, `mode: subagent`, `permission` conforme o domínio do agente — ex.: um agente de Frontend não deveria ter `permission.bash` liberado para mexer em banco de dados).
3. Trocar o `prompt` genérico por algo que referencie essa persona explicitamente, por exemplo:
   ```
   Assuma a persona e as regras definidas em .kilo/agent/${agenteId}.md
   (agente "${agentePerfil.nome}", domínio ${agentePerfil.dominio}).
   Execute a tarefa ${tarefaId}: ${tarefa.titulo}.
   Não assuma outra identidade — se não existir agente configurado para essa
   tarefa, sinalize isso no resultado em vez de inventar um papel.
   ```
   Isso funciona independente de o `agent_manager` aceitar ou não um campo `agent:` estruturado — é a via garantida pela documentação confirmada.

### 4.2 — Verificação que eu mesmo preciso fazer no meu ambiente (não dá pra confirmar de fora)
Inspecionar o schema real da tool `agent_manager` disponível para mim: existe um campo por tarefa (`agent`, ou similar) que force a sessão nova a carregar um custom agent específico desde o início? Se existir, uso isso como reforço além do texto do prompt (defesa em profundidade — texto no prompt sozinho depende de o modelo "obedecer" a instrução; um campo estrutural, se existir, é mais forte).

### 4.3 — Triagem antes de abrir worktree
Adicionar (ou reforçar o uso de) uma checagem antes de eu chamar `agentmap_abrir_worktree`: consultar `agentmap_recomendarAgente` primeiro. Se a resposta indicar que a tarefa é pequena/genérica o suficiente para eu resolver diretamente (isso pode exigir um pequeno ajuste na tool `recomendarAgente.ts` para retornar explicitamente essa opção, se ainda não retornar), eu sigo sem abrir worktree.

### 4.4 — Registrar quando eu tiver que improvisar
Casos vão existir onde o AgentMap não tem um agente configurado pra aquele domínio específico. Nesses casos, em vez de eu inventar silenciosamente uma persona, o comportamento correto é: registrar isso explicitamente (auditoria/log) como "tarefa sem agente configurado — executado com persona genérica", para que isso vire sinal de que falta cadastrar um agente novo no registro — não um comportamento invisível que se repete pra sempre.


## 6. O que não vou fazer

- Não vou forçar todo pedido pequeno a passar por um agente especializado + worktree — isso seria pior do que o problema atual, só trocaria "invento a persona" por "burocracia desnecessária para tudo".
- Não vou modificar o código-fonte do Kilo para isso funcionar — tudo aqui usa APIs e formatos já documentados oficialmente (`kilo.jsonc`, arquivos de custom agent, `agent_manager`).
