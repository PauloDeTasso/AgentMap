## 1. Princípio arquitetural (mantido da proposta revisada, correto)

> **AgentMap governa (é a fonte de verdade dos agentes); Kilo raciocina e executa (via Custom Subagents nativos); Agent Manager isola (worktree/Git quando necessário); nada é inventado silenciosamente.**

Separação de conceitos — esta modelagem está correta e resolve a causa raiz melhor do que meu plano anterior sozinho:

```
Agent (persistente)      → identidade, persona, permissões — vive no AgentMap
Session (efêmera)        → uma execução específica, tem agentId + taskId
Worktree (ambiente físico) → isolamento Git, só existe quando a estratégia exige
```

---

## 2. Três estratégias de execução (mantido, é a resposta correta pra sua ressalva)

```
tarefa chega
   │
   ├─ pequena, sem risco, eu já resolvo → DIRECT (eu mesmo, sem delegar)
   │
   ├─ precisa de especialista, mas não precisa de isolamento Git
   │  → SUBAGENT (task tool, Custom Subagent do AgentMap, sessão isolada
   │    mas sem worktree novo)
   │
   └─ precisa de especialista E de branch/isolamento Git real
      → WORKTREE (Agent Manager, com o Custom Subagent certo)
```

Isso é o que o próprio Kilo já faz nativamente hoje (delegação automática por `description` via `task`, confirmado) — não estamos inventando um mecanismo novo, estamos alimentando o mecanismo existente com as personas certas.

## 3. Implementação em camadas (MVP primeiro — correção de proporcionalidade)

A proposta revisada tinha uma arquitetura completa (TaskEnvelope, AgentManifest, versionamento, 15 gates, máquina de estados nova) que resolve bem o problema, mas é desproporcional para o estágio atual — mesmo raciocínio que já aplicamos antes nesta investigação para descartar Redis/Kafka/Temporal sem necessidade concreta. Divido em camadas: a Camada 1 sozinha já resolve o problema relatado. As demais são evolução, não bloqueio.

### Camada 1 — MVP (resolve o problema relatado, sem infraestrutura nova)

**GATE 0 — Verificação empírica obrigatória antes de qualquer código:**
1. No meu próprio ambiente, inspecionar o schema real da tool `agent_manager` — existe campo `agent:`/`agentName:` por tarefa? (não confirmado por documentação externa, só descubro checando o schema disponível para mim)
2. Confirmar se existe comando de CLI para listar agentes customizados carregados (procurar na minha própria CLI, já que a documentação não confirma isso com certeza)
3. Confirmar que `.kilo/agent/` é de fato a pasta lida pelo meu ambiente (já tenho forte evidência disso, mas validar no projeto específico do AgentMap não custa)

**Implementação:**
1. Em `agentmap_abrir_worktree` (`worktree.ts`), buscar o perfil do agente pelo `tarefa.agenteResponsavel` no registro do AgentMap.
2. Se o Custom Subagent ainda não existir em `.kilo/agent/<agenteId>.md`, gerar usando `KiloAgentGeneratorService.montarMarkdown()` — que já produz o frontmatter `mode:`/`permission:` no formato certo, confirmado compatível com o formato oficial de Custom Subagents.
3. A `description` desse arquivo gerado precisa ser específica e vir do perfil do AgentMap (não genérica) — é o campo que o Kilo usa pra decidir automaticamente qual subagente invocar via `task`, confirmado na documentação.
4. Regra de erro explícita: se `tarefa.agenteResponsavel` não existir no registro, o resultado é `AGENT_NOT_REGISTERED` — não inventar persona, não criar agente genérico. Isso substitui o "registrar como lacuna" (mais vago) do meu plano anterior por um erro estruturado, que é melhor.
5. Triagem antes de abrir worktree: consultar `agentmap_recomendarAgente` primeiro; se a tarefa não justificar especialista, eu mesmo resolvo direto (estratégia DIRECT), sem chamar a tool de worktree.

**Critério de aceitação da Camada 1 (testável, sem infraestrutura nova):**
- Tarefa pequena → eu resolvo direto, sem abrir worktree.
- Tarefa com agente configurado → worktree abre, `.kilo/agent/<agenteId>.md` existe com a persona certa, a sessão nova demonstra ter assumido essa persona (respeita as permissões definidas nela).
- Tarefa com `agenteResponsavel` inexistente no registro → erro `AGENT_NOT_REGISTERED`, não invento nada.

### Camada 2 — Controle de delegação entre agentes (evolução, não bloqueio)

Só depois que a Camada 1 estiver validada: usar `permission.task` (sintaxe confirmada) para controlar explicitamente quem cada agente pode chamar — por exemplo, o agente de Frontend não deveria poder delegar para o de Database. Isso é uma política que o AgentMap já pode ter documentada de forma implícita (relações entre agentes no registro); a Camada 2 só torna isso executável de verdade pelo Kilo, em vez de só uma convenção.

### Camada 3 — Rastreabilidade (evolução)

`taskId`/`sessionId`/`parentSessionId` já existem em parte no que construímos para o wake-up (`event_sequence`, `eventBus`). Estender esse mesmo mecanismo para registrar qual persona/versão de agente foi usada em cada delegação, em vez de criar um `TaskEnvelope`/`AgentManifest` novo do zero. Reaproveitar antes de criar estrutura paralela — mesmo princípio de "não duplicar o que já existe" que já apliquei ao revisar o `KiloAgentGeneratorService`.

### O que eu deliberadamente NÃO faria agora
- `AgentManifest` com `manifestHash` e versionamento (`backend@3`) — só faz sentido quando o registro de agentes já estiver mudando com frequência suficiente para isso importar na prática. Hoje seria complexidade sem uso real.
- Máquina de estados nova (`REQUESTED → RESOLVING → AUTHORIZED → ...`) — o AgentMap já tem estados de tarefa; usar os que já existem até provar que não bastam.

## 6. Regras que não mudam independente da camada

1. Todo agente executado automaticamente precisa ter `agentId` registrado no AgentMap.
2. Eu posso executar diretamente tarefas dentro da minha capacidade — delegação não é obrigatória para tarefas pequenas.
3. Quando eu delegar, uso o Custom Subagent gerado a partir do perfil do AgentMap — nunca invento persona.
4. Ausência de agente configurado é um erro estruturado (`AGENT_NOT_REGISTERED`), não uma lacuna que eu preencho sozinho.
5. Worktree é ambiente de execução de uma sessão, não é a identidade do agente.
6. Não modifico código-fonte do Kilo para nada disso funcionar — tudo usa mecanismos já documentados oficialmente (Custom Subagents, `task`, `permission.task`, Agent Manager).
