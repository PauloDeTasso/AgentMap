# Plano Final do Projeto AgentMap — v1.1.0 (Corrigido contra documentação real do Kilo Code)

> **Versão:** 1.1.0
> **Data:** 2026-08-27
> **Branch:** v0044
> **Status:** Revisão técnica — corrige premissa de descoberta automática não verificada
> **Ideia Central:** AgentMap como template/base "copiar e colar" por projeto, não gerenciador multi-tenant

---

## 0. Resumo da Revisão

O plano v1.0.1 acertou o diagnóstico (multi-tenant é complexidade desnecessária) e a direção (template local por projeto). Mas ele tem **uma falha crítica não verificada** que compromete exatamente o requisito mais importante que você definiu: *"copiar e colar na raiz de qualquer projeto e os agentes vão saber trabalhar, usar as tools no MCP, as APIs, os recursos, a comunicação padrão do AgentMap."*

**A falha:** o plano assume que colocar tudo dentro de `.ia/` é suficiente para o Kilo Code "descobrir" o MCP server, as instruções e os subagentes do AgentMap. **Isso é falso.** O Kilo Code não varre pastas arbitrárias do projeto. Ele só carrega configuração de um conjunto fixo e documentado de caminhos na raiz. Se o AgentMap inteiro (config incluída) fica dentro de `.ia/`, **nenhum agente vai carregá-lo automaticamente** — o "copiar e colar" do jeito que está desenhado no v1.0.1 não funciona na prática.

Esta revisão mantém 100% da ideia central (template desacoplado, single-project, sem multi-tenancy) e corrige a mecânica de integração com base em documentação oficial do Kilo Code (VS Code, CLI e formato `kilo.jsonc`), citada seção por seção.

---

## 1. Ideia Central (mantida, não negociável)

### 1.1 Problema identificado (mantido do v1.0.1)

O AgentMap atual se comporta como sistema multi-tenant centralizado: `ProjetoService` como façade global, `GERENCIADOR_DIR` apontando para pasta base, `projectMiddleware` recriando serviços a cada request. Toda atualização do AgentMap exige tocar também no mecanismo de criação de projeto — manutenção duplicada, risco de inconsistência.

### 1.2 Solução proposta (mantida, com uma correção de mecânica)

**AgentMap continua sendo um template/base copiado para a raiz de cada projeto.** O que muda é *como* ele se conecta ao Kilo Code — isso não pode ficar só dentro de `.ia/`; precisa de uma **camada fina de integração na raiz do projeto**, porque é só ali que o Kilo Code procura.

### 1.3 Falha crítica identificada e correção

O Kilo Code carrega configuração e comportamento a partir de um conjunto fixo de arquivos/pastas na raiz (ou em `.kilo/`), não de qualquer subpasta arbitrária:

| O que o agente precisa saber | Onde o Kilo Code realmente procura | Você pode colocar em `.ia/`? |
|---|---|---|
| Instruções gerais do projeto | `AGENTS.md` na raiz (arquivo único, "README para agentes"); também aceita `AGENTS.md` em subpastas, carregado *dinamicamente* só quando o agente lê um arquivo daquela subpasta | Não como arquivo principal — mas subpastas de `.ia/` podem ter seus próprios `AGENTS.md` que são carregados sob demanda |
| Config unificada (regras, permissões, agentes, MCP) | `kilo.jsonc` na raiz, ou `.kilo/kilo.jsonc` (se ambos existem, `.kilo/kilo.jsonc` vence) | Não — tem que estar num desses dois caminhos exatos |
| Servidores MCP | Dentro de `kilo.jsonc`/`.kilo/kilo.jsonc`, chave `mcp` (formato atual); formato legado ainda aceito em `.kilocode/mcp.json`, chave `mcpServers` | Não — precisa estar num desses dois lugares |
| Regras adicionais (arquivos de texto) | Referenciadas pelo array `instructions` dentro do `kilo.jsonc`, tipicamente apontando para `.kilo/rules/*.md` | Sim, o **conteúdo** pode morar em `.ia/`, desde que `instructions` no `kilo.jsonc` aponte para lá |
| Subagentes customizados (papéis: Arquiteto, Backend, Frontend etc.) | Arquivos `.md` com frontmatter YAML em `.kilo/agent/`, `.kilo/agents/` ou `.kilocode/agents/` | Não como diretório principal — o Kilo só varre esses três caminhos |
| Comandos/slash-workflows | `.kilo/commands/*.md` | Não — caminho fixo |

Fontes consultadas nesta revisão: documentação oficial de customização (`kilo.ai/docs/customize/agents-md`, `custom-instructions`, `custom-rules`, `custom-modes`), documentação de MCP (`kilo.ai/docs/automate/mcp/using-in-kilo-code`, `using-in-cli`), guia de configuração `kilo.jsonc` (2026), e o próprio código-fonte do Kilo Code (`Kilo-Org/kilocode`).

**Consequência prática:** o template do AgentMap precisa gerar (ou manter sincronizados) alguns arquivos **fora** de `.ia/`, na raiz do projeto:

```
MEU_PROJETO/
├── AGENTS.md                      ← gerado pelo `agentmap init`, aponta para .ia/docs/
├── kilo.jsonc                     ← gerado/mesclado pelo `agentmap init`/`update`
│                                      (instructions, mcp, permission)
├── .kilo/
│   ├── agent/                     ← subagentes gerados a partir de .ia/agentes/*.json
│   │   ├── arquiteto.md
│   │   ├── backend.md
│   │   ├── frontend.md
│   │   └── ...
│   ├── rules/                     ← symlink/cópia sincronizada de .ia/politicas/*.md
│   └── commands/                  ← slash-commands do AgentMap (ex: /handoff, /status)
├── .ia/                           ← motor do AgentMap (dados, docs, backend MCP)
│   ├── agentmap.json
│   ├── backend/                   ← código do MCP server (precisa build antes de rodar)
│   ├── agentes/                   ← definições canônicas (fonte de verdade)
│   ├── contratos/ tarefas/ handoffs/ ...  (igual ao v1.0.1)
│   └── docs/
├── backend/                        ← backend do projeto em si (se houver)
├── frontend/
└── docs/
```

`.ia/` continua sendo a **fonte de verdade portátil** (dados, histórico, docs, código do MCP server). Os arquivos na raiz (`AGENTS.md`, `kilo.jsonc`, `.kilo/agent/*`) são **artefatos gerados/derivados**, recriados por `agentmap init`/`agentmap update` a partir do conteúdo de `.ia/`. Isso preserva a ideia original — "atualizar o template = atualizar todos os projetos" — porque quem muda é o gerador dentro de `.ia/`, e os arquivos-satélite na raiz são regravados automaticamente.

Isso também resolve o problema de manutenção duplicada do v1.0.1 sem violar a forma como o Kilo Code realmente descobre coisas.

### 1.4 Benefícios (mantidos do v1.0.1)

| Benefício | Explicação |
|---|---|
| Simplicidade | Backend serve um projeto apenas, sem `projectMiddleware` |
| Manutenibilidade | Atualizar `.ia/` regenera os satélites em todos os projetos |
| Desacoplamento | Projetos não dependem de instância central |
| Descoberta automática real | Agora garantida pelos caminhos corretos, não por suposição |
| Offline-first real | Projeto autossuficiente após `agentmap init` |

### 1.5 Desvantagens e mitigações (revisado)

| Desvantagem | Mitigação |
|---|---|
| Arquivos gerados na raiz podem ser editados manualmente pelo usuário e depois sobrescritos no `update` | `agentmap update` faz **merge**, não overwrite (ver seção 2.5); seções geradas são marcadas com comentário `// gerado pelo agentmap — não editar manualmente` dentro dos blocos específicos |
| `kilo.jsonc` é JSONC (permite comentários) — um merge ingênuo com `JSON.parse` quebra o arquivo do usuário | Usar parser que preserva comentários (ex: `jsonc-parser`, já usado pelo próprio Kilo Code) — ver T-novo na seção 5 |
| MCP server local exige build (`npm run build`) antes do Kilo Code conseguir spawná-lo via stdio | `agentmap init` roda `npm install && npm run build` dentro de `.ia/backend/` como parte do bootstrap, não como passo manual |
| Divergência entre formato legado (`.kilocode/mcp.json`, chave `mcpServers`) e formato atual (`kilo.jsonc`, chave `mcp`) pode gerar duplicidade ou servidor não carregado dependendo da versão da extensão instalada | `agentmap init` detecta a versão/format existente no projeto (se já houver `kilo.jsonc` ou `.kilocode/mcp.json`) e escreve no formato compatível; documentar isso explicitamente nas docs do AgentMap |
| **Contradição interna no v1.0.1:** a Opção 1 de propagação de atualizações era "git submodule", que exige repositório próprio publicado e `git submodule update --init --remote` — isso vai contra o requisito explícito de "só copiar e colar" | Submodule vira **opção avançada opcional** para times, não o caminho padrão. O caminho padrão é `npx agentmap update` copiando/mesclando arquivos localmente, sem depender de Git remoto |
| Múltiplas instâncias do MCP server (uma por projeto aberto simultaneamente no VS Code) consomem mais memória que uma instância central | Aceitável — é o preço do desacoplamento; documentar como trade-off consciente, não como risco escondido |

## 2. Arquitetura Alvo (Corrigida)

### 2.1 Modelo em duas camadas

1. **Motor (`.ia/`)** — portátil, é o que você copia e cola. Contém dados (contratos, tarefas, handoffs...), documentação e o código-fonte do backend MCP. É a fonte de verdade.
2. **Integração (raiz do projeto)** — `AGENTS.md`, `kilo.jsonc` (ou `.kilo/kilo.jsonc`), `.kilo/agent/*.md`, `.kilo/rules/*`, `.kilo/commands/*`. É **gerada** a partir do motor pelo `agentmap init`/`update`. É o que o Kilo Code realmente lê.

Isso separa claramente "o que eu copio" de "o que o Kilo Code exige que exista em caminhos fixos" — o v1.0.1 misturava os dois e assumia que bastava a cópia.

### 2.2 Tabela de mapeamento motor → integração

| Fonte em `.ia/` | Gerado para | Quando regenerar |
|---|---|---|
| `.ia/agentes/*.json` (definição canônica de cada papel) | `.kilo/agent/*.md` (frontmatter YAML + prompt) | A cada `agentmap init`/`update`, ou quando um agente é criado/editado via API do AgentMap |
| `.ia/docs/visao-geral.md`, `.ia/fluxo-trabalho.md` | `AGENTS.md` (raiz) — resumo + link explícito para `.ia/docs/` | A cada `update`; usuário pode adicionar uma seção manual protegida no fim do arquivo |
| `.ia/backend/dist/mcp-server/main.js` (após build) | Entrada `mcp.agentmap` dentro de `kilo.jsonc` | No `init`; recriada no `update` só se o caminho/comando mudou |
| `.ia/politicas/*.md` | `.kilo/rules/agentmap-*.md` (cópia, não symlink — Windows lida mal com symlink sem privilégio elevado) | A cada `update` |
| `.ia/procedimentos/*.md` | `.kilo/commands/*.md` (slash-commands, ex: `/handoff`, `/status`) | A cada `update` |

### 2.3 Backend simplificado (mantido do v1.0.1)

```typescript
// main.ts — simples, serviços singleton, um projeto por processo
const services = createServices();
const apiRouter = createApiRouter(services);
const mcpRouter = createMcpRouter(services); // exposto via stdio para o Kilo Code

app.use('/api', apiRouter);
app.listen(3150, () => console.log('AgentMap rodando em http://localhost:3150'));
```

Sem `ProjetoService` central, sem `projectMiddleware`, sem `GERENCIADOR_DIR`. Isso continua correto e é independente da correção da seção 1.3.

### 2.4 Comandos corrigidos

```bash
# Copiar o motor para a raiz de um projeto novo ou existente
cp -r agentmap-template/.ia ./MEU_PROJETO/.ia

# Gerar a camada de integração (isso é o passo que faltava no v1.0.1)
cd MEU_PROJETO
npx agentmap init
#  → roda npm install && npm run build dentro de .ia/backend/
#  → gera/mescla AGENTS.md, kilo.jsonc (ou .kilo/kilo.jsonc), .kilo/agent/*.md,
#    .kilo/rules/*, .kilo/commands/*
#  → detecta formato de MCP já presente no projeto (novo vs legado) e respeita

# Depois disso, o Kilo Code (VS Code, CLI ou JetBrains) já reconhece o AgentMap
# na próxima recarga da janela — sem passo manual adicional.
```

```bash
# Atualizar o motor (nova versão do AgentMap) e propagar para a integração
npx agentmap update
#  → substitui o conteúdo de .ia/ pela nova versão do template
#  → re-executa a geração da camada de integração com merge preservando
#    edições manuais feitas fora das seções marcadas como geradas
```

### 2.5 Propagação de atualizações (revisado)

**Caminho padrão (o que você pediu — copiar e colar):**
```bash
npx agentmap update   # sincroniza .ia/ + regenera raiz via merge JSONC-safe
```

**Caminho opcional para times (não é o padrão):**
```bash
git submodule update --remote .ia/   # só se o time já usa Git submodules por outro motivo
```

O v1.0.1 apresentava submodule como "Opção 1", implicando prioridade. Isso contradiz o requisito de simplicidade — fica reclassificado como avançado/opcional.

## 7. Riscos Revisados

### 7.1 Riscos eliminados (mantidos do v1.0.1)

| Risco antes | Status | Motivo |
|---|---|---|
| Projeto aberto/fechado inconsistente | Eliminado | Single-project não tem esse estado |
| `projectMiddleware` recria serviços | Eliminado | Serviços singleton |
| Duas instâncias de `MonitoramentoService` | Eliminado | Apenas uma instância |
| `GERENCIADOR_DIR` e multi-tenancy | Eliminado | Não existe mais |
| Path traversal entre projetos | Eliminado | Apenas um projeto |

### 7.2 Riscos novos (revisado — inclui os que o v1.0.1 não via)

| Risco | Probabilidade | Impacto | Mitigação |
|---|---|---|---|
| **"Copiar e colar" não é reconhecido pelo Kilo Code (falha do v1.0.1)** | Era certeza, agora eliminado | Alto | Corrigido pela camada de integração (seção 2) |

## 10. Conclusão

A ideia central do v1.0.1 estava certa: **AgentMap deve ser um template local por projeto, não um gerenciador multi-tenant centralizado.** Essa revisão não muda essa direção — ela corrige a única peça que, se não ajustada, faria o objetivo principal (copiar `.ia/`, colar na raiz, e os agentes já saberem trabalhar) falhar silenciosamente: o Kilo Code só descobre configuração em caminhos fixos (`AGENTS.md`, `kilo.jsonc`/`.kilo/kilo.jsonc`, `.kilo/agent/`, `.kilo/rules/`, `.kilo/commands/`), nunca em subpastas arbitrárias como `.ia/`.

A solução — motor portátil em `.ia/` + camada fina de integração gerada na raiz — preserva integralmente a filosofia "atualizar o template = atualizar todos os projetos", só move a fonte de verdade um nível abaixo e adiciona um gerador que escreve nos lugares certos.

**Próxima ação recomendada:** antes de aprovar o roadmap completo, rodar o spike de validação da seção 9.1 (dia 1) em um projeto de teste real, para confirmar empiricamente — não só via documentação — que a extensão do Kilo Code instalada localmente reconhece `kilo.jsonc` + `.kilo/agent/` sem passo manual adicional. Documentação pode estar um passo à frente ou atrás da versão instalada.
