Perfeito. Com a verificação adicional da documentação oficial atual do Kilo, eu consolidaria o projeto em um **plano único, atualizado e implementável**, eliminando as hipóteses que ficaram para trás.

A mudança central é esta:

> **O AgentMap será a fonte de verdade dos agentes; o Kilo Custom Subagents será o mecanismo oficial de identidade/delegação; o agente principal continuará autônomo para tarefas pequenas; e o Agent Manager será usado para isolamento/worktrees quando realmente necessário.**

Isso aproveita mecanismos que o Kilo já possui, em vez de criar um segundo sistema paralelo. A documentação atual confirma `task` para subagentes, Custom Subagents, permissões de delegação e Agent Manager com sessões isoladas em worktrees. ([Kilo][1])

# PLANO COMPLETO E ATUALIZADO — INTEGRAÇÃO OFICIAL DOS AGENTES DO AGENTMAP COM KILO CODE

## 0. Objetivo definitivo

Corrigir o comportamento atual em que o agente principal:

```text
recebe tarefa
    ↓
decide que precisa de outro agente
    ↓
abre Agent Manager
    ↓
cria/executa um agente genérico ou inventado
    ↓
atribui contexto/persona próprios
```

para:

```text
                    TAREFA
                       │
                       ▼
              AGENTE PRINCIPAL
                       │
             ┌─────────┴─────────┐
             │                   │
          simples          especializada
             │                   │
             ▼                   ▼
         EXECUTA             KILO TASK
         DIRETO                  │
                                 ▼
                         CUSTOM SUBAGENT
                                 │
                         agente do AgentMap
                                 │
                     ┌───────────┴───────────┐
                     │                       │
                 sem worktree            worktree
                     │                       │
                     ▼                       ▼
               sessão isolada          Agent Manager
                                             │
                                             ▼
                                          WORKTREE
```

### Resultado desejado

O agente principal **não perde autonomia**.

Ele pode:

* ler arquivos;
* editar;
* executar comandos;
* testar;
* corrigir pequenos problemas;
* fazer alterações simples;
* resolver tarefas que já domina;

sem chamar ninguém.

Quando uma tarefa realmente se beneficiar de especialização, ele poderá delegar.

Mas:

> **a identidade do especialista não será inventada pelo agente principal.**

Será uma identidade existente no AgentMap e materializada como Custom Subagent do Kilo.

# 1. Base factual da arquitetura

A documentação oficial atual do Kilo confirma:

### Custom Subagents

Podem ser definidos em arquivos como:

```text
.kilo/agents/backend.md
.kilo/agent/backend.md
.kilocode/agents/backend.md
```

e também em configuração do Kilo. O nome do arquivo determina o nome do agente. ([Kilo][2])

Eles possuem configuração de:

```text
description
mode
permission
prompt
model
```

e podem ser utilizados pelo mecanismo `task`. ([Kilo][1])

### Delegação automática

Agentes primários podem invocar subagentes via `Task` quando a descrição do subagente corresponde à tarefa. ([Kilo][1])

### Permissões

A permissão `task` pode restringir explicitamente quais subagentes um agente pode chamar:

```yaml
permission:
  task:
    "*": deny
    "backend": allow
    "security": allow
```

([Kilo][3])

### Agent Manager

O Agent Manager fornece sessões isoladas em Git worktrees e pode executar múltiplas tarefas paralelamente. A ferramenta `agent_manager` aceita tarefas com `prompt`, `name` ou `branchName`, além de configuração de modelo/variant; a documentação pública atual **não documenta um parâmetro `agent` para selecionar diretamente um Custom Subagent**. ([Kilo][4])

### Orchestrator

O antigo Orchestrator está deprecated. O Kilo passou a permitir que agentes com acesso completo deleguem diretamente através de `task`. ([Kilo][5])

Portanto:

> **não vamos construir a arquitetura nova do AgentMap sobre o antigo Orchestrator.**

---

# 2. Arquitetura de responsabilidades

A partir deste plano, cada componente terá uma responsabilidade precisa.

| Componente                    | Responsabilidade                                             |
| ----------------------------- | ------------------------------------------------------------ |
| **AgentMap Registry**         | Fonte oficial dos agentes                                    |
| **AgentMap Profile**          | Identidade, personalidade, contexto, skills, permissões etc. |
| **KiloAgentGeneratorService** | Converter perfil AgentMap → Custom Subagent Kilo             |
| **Kilo Custom Subagents**     | Identidade executável dos especialistas                      |
| **Kilo Primary Agent**        | Raciocinar, executar diretamente e decidir quando delegar    |
| **Kilo `task`**               | Criar sessão isolada de subagente                            |
| **AgentMap MCP**              | Descoberta, governança, consulta e controle                  |
| **Agent Manager**             | Worktrees e sessões que precisam de isolamento Git           |
| **Git**                       | Branch/worktree/código                                       |
| **Watcher/Event System**      | Detectar conclusão e acordar o principal                     |

A regra arquitetural será:

> **AgentMap governa; Kilo raciocina e executa; Agent Manager isola; Git controla o código.**

# 3. O AgentMap será a Source of Truth

O AgentMap já possui:

```text

esquemas/agente-perfil.schema.json
```

e:

```text
KiloAgentGeneratorService
```

Esses elementos passam a ser oficialmente responsáveis pela identidade dos agentes.

O Kilo **não será a fonte de verdade**.

O arquivo:

```text
.kilo/agents/backend.md
```

será um **artefato derivado**.

A fonte será:

```text
AgentMap
   ↓
Agent Registry
   ↓
Agent Profile
```

# 4. Identidade única

Cada agente deverá possuir um identificador estável:

```text
agentId
```

Esse identificador deverá representar a mesma identidade em todos os níveis:

```text
AgentMap
   ↓
agentId = backend
   ↓
Kilo
   ↓
backend.md
   ↓
Custom Subagent = backend
```

Não pode existir:

```text
AgentMap = backend
Kilo = java-specialist
Agent Manager = worker-42
```

como se fossem três identidades diferentes.

Podem existir:

```text
agentId = backend
sessionId = abc123
worktree = agent-backend-abc123
```

porque:

* `agentId` = identidade;
* `sessionId` = execução;
* `worktree` = ambiente físico.

# 7. A descrição será crítica

A documentação do Kilo informa que a `description` ajuda o agente primário a selecionar o subagente adequado automaticamente. ([Kilo][1])

Portanto, a descrição não pode ser genérica:

```text
"Agente backend."
```

Deve explicar claramente:

```text
especialidade
responsabilidade
tipos de tarefas
quando utilizar
limites
```

Exemplo conceitual:

```text
Especialista responsável por implementação e manutenção
de APIs REST, regras de negócio, persistência e integrações
do backend Java/Spring do projeto. Deve ser utilizado para
tarefas que envolvam código de backend, serviços, controllers,
repositories, segurança e integração com PostgreSQL.
```

**A descrição deverá vir do AgentMap**, não ser inventada pela sessão.

# 8. Personalidade

A personalidade também deverá vir do AgentMap.

O Custom Subagent terá seu próprio prompt de sistema.

Portanto, não fazer:

```text

```

A identidade deverá estar no Custom Subagent.

A tarefa deve ser somente a tarefa.

Conceitualmente:

```text
CUSTOM SUBAGENT

IDENTIDADE
PERSONALIDADE
CONTEXTO
REGRAS
PERMISSÕES
CAPABILIDADES

+

TASK
    ↓
"Implemente X"
```

Isso elimina a mistura entre:

```text
identidade
```

e:

```text

```


```text

 └── security

 ├── database
 └── security
```

Isso será traduzido para:

```yaml

  task:
    "*": deny
    "backend": allow
    "frontend": allow
    "security": allow
```

quando aplicável.

O Kilo já possui esse mecanismo nativamente. ([Kilo][3])

# 17. Três estratégias de execução

O AgentMap deverá distinguir conceitualmente:

```text
DIRECT
SUBAGENT
WORKTREE
```

### DIRECT

```text
principal → executa
```

Para:

* pequenas correções;
* leitura;
* análise simples;
* pequenos edits;
* comandos simples;
* tarefas que não justificam isolamento.

### SUBAGENT

```text
principal
   ↓
task
   ↓
Custom Subagent
```

Para:

* especialização;
* análise paralela;
* investigação;
* subtarefas;
* trabalho que não precisa de uma alteração Git isolada.

### WORKTREE

```text
principal
   ↓
Agent Manager
   ↓
worktree
   ↓
sessão
```

Para:

* implementação independente;
* alteração grande;
* trabalho paralelo;
* branch isolada;
* necessidade real de isolamento Git.

O Agent Manager é especificamente destinado a sessões isoladas em worktrees. ([Kilo][4])

# 30. `requestDispatch`

A operação deve significar:

> "Solicito que uma tarefa seja executada pelo agente registrado X."

E não:

> "Crie um agente X."

Conceitualmente:

```text
requestDispatch(
    taskId,
    requesterAgentId,
    targetAgentId,
    parentSessionId
)
```

O AgentMap valida:

```text
agent existe?
requester existe?
target existe?
requester pode chamar target?
target está ativo?
task é válida?
```

Somente depois:

```text
dispatch
```

# 58. A regra definitiva do AgentMap

Eu colocaria esta regra no próprio contrato arquitetural:

```text
AGENTMAP AGENT GOVERNANCE

1. Todo agente executado automaticamente deve possuir agentId
   registrado no AgentMap.

2. O agente principal pode executar diretamente tarefas que
   estejam dentro de sua capacidade.

3. Delegação não é obrigatória para tarefas pequenas.

4. Quando delegar, o principal deve utilizar Custom Subagents
   registrados pelo AgentMap.

5. Nenhuma persona, identidade ou agente deve ser inventado
   silenciosamente durante a execução.

6. A identidade do agente vem do AgentMap.

7. A definição executável do agente é materializada através
   do mecanismo oficial de Custom Subagents do Kilo.

8. A permissão de delegação deve ser controlada pelo Kilo
   e pela política do AgentMap.

9. Agent Manager é infraestrutura de sessão/worktree,
   não autoridade de identidade.

10. Worktree não representa um agente; representa um ambiente
    de execução de uma sessão.

11. Ausência de especialista deve ser registrada como lacuna,
    não resolvida pela invenção de um agente.

12. Toda execução especializada deve ser rastreável por:
    taskId, agentId, sessionId e parentSessionId.
```

# 59. O que eu considero a solução final

A solução não é:

> **"impedir o Kilo de criar agentes."**

É melhor:

> **"fazer com que os agentes que o Kilo conhece sejam exatamente os agentes oficiais do AgentMap e deixar o mecanismo nativo de Custom Subagents do Kilo decidir quando uma especialização é útil."**

Assim conseguimos simultaneamente:

**Autonomia**

```text
tarefa pequena
→ principal resolve
```

**Especialização**

```text
tarefa complexa
→ Custom Subagent
```

**Identidade**

```text
Custom Subagent
→ AgentMap
```

**Segurança**

```text
permission.task
→ limita delegação
```

**Isolamento**

```text
Agent Manager
→ worktree quando necessário
```

**Rastreabilidade**

```text
AgentMap
→ task/session/event
```

**Wake-up**

```text
especialista termina
→ evento
→ principal continua
```

E, principalmente, **não estamos criando um orquestrador paralelo ao Kilo**. Estamos integrando o AgentMap aos mecanismos que o Kilo já oferece oficialmente: Custom Subagents, `task`, permissões e Agent Manager. O próprio Kilo atualmente recomenda esse modelo em vez do antigo Orchestrator, que está deprecated. ([Kilo][5])
