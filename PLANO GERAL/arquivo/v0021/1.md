Sim. E, depois de conferir a documentação atual do Kilo Code e separar o que é **comportamento documentado** do que seria apenas uma hipótese arquitetural, eu faria o AgentMap dessa forma.

Há uma correção importante em relação ao que eu disse antes: **o Kilo Code realmente possui mecanismos nativos para subagentes e delegação**. Custom agents podem ser `primary`, `subagent` ou `all`; agentes `subagent` são invocados pelo agente principal através da ferramenta `task`, executam em sessão isolada e devolvem o resultado ao agente pai. Além disso, o Kilo permite restringir explicitamente quais subagentes cada agente pode chamar através da permissão `task`. ([Kilo][1])

E isso nos dá uma solução muito melhor para o AgentMap.

# PLANO DEFINITIVO — GOVERNANÇA DE AGENTES DO AGENTMAP

## 1. Princípio arquitetural

Eu estabeleceria esta regra como **invariante do sistema**:

> **O agente principal continua sendo autônomo e pode executar diretamente qualquer tarefa que esteja dentro de sua capacidade. Quando precisar de especialização, ele só pode delegar para agentes registrados e autorizados pelo AgentMap.**

Portanto, **não queremos transformar o agente principal em um simples despachante**.

Queremos:

```text
                    AGENTE PRINCIPAL
                           │
              ┌────────────┴────────────┐
              │                         │
        tarefa simples             tarefa especializada
              │                         │
              ▼                         ▼
        EXECUTA DIRETO             CONSULTA AGENTMAP
                                        │
                                        ▼
                                AGENTE REGISTRADO
                                        │
                                        ▼
                                   DELEGAÇÃO
                                        │
                                        ▼
                                    WORKTREE
```

Essa é a solução para a sua interrogação.

### Não:

```text
toda tarefa → chama subagente
```

### Nem:

```text
toda tarefa → agente principal faz tudo
```

### Mas:

```text
tarefa
   ↓
avaliar necessidade de delegação
   ↓
┌──────────────────────────────┐
│ pode resolver sozinho?       │
└──────────────┬───────────────┘
        SIM    │    NÃO
         ↓     │     ↓
    principal  │  AgentMap
               │     ↓
               │ agente especializado
               │     ↓
               │ execução
```

---

# 2. O que a documentação do Kilo confirma

Isso é importante porque você pediu especificamente **realidade, não achismo**.

O Kilo documenta atualmente que:

* agentes customizados podem ser definidos como `primary`, `subagent` ou `all`;
* subagentes são executados em **sessões isoladas**;
* o agente principal pode invocá-los usando a ferramenta `task`;
* o resultado retorna para o agente pai;
* a descrição do agente é usada pelo mecanismo de delegação para ajudar a selecionar o subagente;
* a permissão `task` pode restringir exatamente quais agentes um agente pode chamar;
* o Kilo permite `kilo agent list`;
* o CLI possui `kilo agent create`;
* configurações de agentes podem vir de várias camadas, inclusive projeto e `.kilo/agents/`. ([Kilo][1])

Isso significa que **o próprio Kilo já possui quase todos os primitives necessários para implementar o comportamento que queremos**.

Não precisamos inventar um mecanismo paralelo de agentes.

---

# 3. O problema real do AgentMap

O problema que você está observando não é simplesmente:

> "Kilo cria agentes."

O problema arquitetural é:

> **o ciclo de delegação do Kilo não está subordinado ao registro de agentes do AgentMap.**

Consequentemente, existe potencialmente:

```text
Kilo
 │
 ├── Agent A
 ├── Agent B
 ├── Agent C
 ├── agente inventado
 ├── agente temporário
 └── agente com prompt diferente
```

enquanto o AgentMap possui:

```text
AgentMap
 │
 ├── principal
 ├── frontend
 ├── backend
 ├── database
 ├── security
 └── ...
```

Temos duas autoridades.

Isso precisa acabar.

---

# 4. Nova regra: AgentMap Registry

O AgentMap passa a possuir um:

```text
Agent Registry
```

Esse registro é a **fonte oficial dos agentes do sistema**.

Cada agente possui um identificador estável:

```text
agentId
```

Por exemplo:

```text
principal
frontend
backend
database
security
```

Os nomes reais devem ser os que já existem no seu AgentMap; **não devemos inventar novos nomes durante a implementação**.

---

# 5. AgentMap passa a ser a autoridade da identidade

Para cada `agentId`, o AgentMap controla:

```text
identity
personality
context
instructions
role
capabilities
skills
tools
permissions
contracts
model
runtimePolicy
worktreePolicy
```

O Kilo não deve reconstruir essas informações por conta própria.

A ideia é:

```text
agentId
   ↓
AgentMap
   ↓
Agent Definition
   ↓
Execution
```

e não:

```text
agentId
   ↓
Kilo inventa configuração
   ↓
Execution
```

# 6. Mas existe uma particularidade importante do Kilo

Aqui está uma consequência real da documentação que precisamos respeitar.

O Kilo trabalha com **definições de agentes** através de arquivos Markdown/configuração, incluindo `.kilo/agents/*.md` e `kilo.jsonc`. O conteúdo do Markdown é usado como prompt de sistema do agente. ([Kilo][2])

Portanto, não basta dizer:

```text
"AgentMap sabe que backend existe."
```

Precisamos fazer o runtime do Kilo **enxergar o backend exatamente como o AgentMap definiu**.

É aqui que entra a integração.

# 9. Usar a permissão `task`

Essa é uma das partes mais importantes do plano.

O Kilo documenta que a permissão `task` pode ser configurada para permitir ou negar subagentes específicos. ([Kilo][4])

Então podemos chegar a:

```yaml

    "*": deny
    "frontend": allow
    "backend": allow
    "database": allow
    "security": allow
```

Naturalmente, os IDs precisam corresponder aos agentes reais do AgentMap.

Isso transforma:


```text

```

Assim o agente principal não possui acesso universal.

# 40. O resultado arquitetural que eu buscaria

No final, quero que seja impossível ocorrer isto:

```text
Kilo Principal
   ↓
"vou criar um especialista Java"
   ↓
Kilo cria agente
   ↓
prompt inventado
   ↓
personalidade inventada
   ↓
worktree
```

O fluxo permitido será:

```text
Kilo Principal
       │
       ├── consigo fazer?
       │       │
       │      SIM
       │       ↓
       │    executa
       │
       └── NÃO
            ↓
       AgentMap
            ↓
       encontrar agente
            ↓
       autorização
            ↓
       AgentManifest
            ↓
       dispatch
            ↓
       Agent Manager
            ↓
       Worktree
            ↓
       agente oficial
            ↓
       resultado
            ↓
       AgentMap
            ↓
       wake principal
```

## A decisão que eu considero definitiva

**Eu não faria o AgentMap tentar substituir a inteligência do Kilo.**

O Kilo deve continuar podendo pensar:

> "Isso é simples, faço eu."

E também:

> "Isso exige uma especialização que eu não tenho; vou delegar."

Mas quando decidir delegar:

> **ele não escolhe/cria uma identidade de agente por conta própria. Ele solicita ao AgentMap uma execução de um agente que já existe e que está autorizado para aquela relação de delegação.**

Isso preserva a autonomia do principal **sem abrir mão da governança centralizada do AgentMap**.

E é compatível com o que o Kilo realmente documenta hoje: subagentes, sessões isoladas, `task`, agentes `subagent` e controle de delegação por `permission.task`. ([Kilo][1])

**Eu considero essa a arquitetura-alvo para o AgentMap.** O próximo trabalho de implementação não deve começar alterando código às cegas: o **GATE 0 precisa inspecionar o repositório real do AgentMap e o fluxo real Kilo → MCP → Agent Manager → worktree**, mapear exatamente os pontos existentes e, só então, transformar este plano em tarefas de implementação sem inventar componentes que o projeto já possua.
