# Plano — MCP 2026 Preparação e Dual-Era Support

> **Ordem:** 2/5  
> **Prioridade:** Alta  
> **Depende de:** `1786789347005-mcp-resource-subscriptions-plan.md`  
> **Stack:** Node.js + TypeScript + Express + MCP Server + Kilo Code  
> **SDK atual:** `@modelcontextprotocol/sdk` v1.30.0  
> **SDK MCP 2026:** não disponível no npm ainda (não há v2 publicada)

---

## 1. Objetivo

Preparar o AgentMap para suportar clientes MCP 2026-07-28 (`subscriptions/listen`) **sem quebrar** clientes MCP 2025 (`resources/subscribe`). Como o SDK v2 ainda não está disponível, a preparação consiste em estruturar o código para migração incremental, não em reescrever funcionalidades.

## 2. Constatação importante

- O npm não publica `@modelcontextprotocol/sdk` v2 ainda. A versão mais recente é `1.30.0`.
- O SDK v1 suporta: `resources/subscribe`, `resources/unsubscribe`, `sendResourceUpdated`, `sendResourceListChanged`.
- O MCP 2026-07-28 introduz `subscriptions/listen`, que **não existe no SDK atual**.
- Portanto, a "migração para MCP 2026" no momento é **preparação estrutural**, não reescrita funcional.

## 3. Decisões arquiteturais

1. **Dual-era runtime:** manter `resources/subscribe` funcionando hoje; quando o SDK v2 sair, adicionar `subscriptions/listen` em paralelo.
2. **Sem breaking changes:** clientes atuais (Kilo Code, VS Code, MCP Inspector) continuam funcionando com MCP 2025.
3. **Capabilities discovery:** negociar capabilities via `initialize`; se o cliente suportar `subscriptions`, usar o novo protocolo; senão, fallback para legacy.
4. **Serviços de domínio isolados:** continuam publicando no `EventBus` sem saber se o transporte é 2025 ou 2026.
5. **Feature flag por cliente:** armazenar preferência de protocolo por session no `SubscriptionManager`.

## 4. Tarefas

### Fase 1 — Análise do SDK atual

1. **Mapear API do SDK v1.30.0**
   - Confirmar métodos disponíveis: `sendResourceUpdated`, `sendResourceListChanged`, `setRequestHandler`
   - Confirmar que NÃO existem: `subscriptions/listen`, `subscribeToResources`, etc.
   - Documentar em `docs/arquitetura-mcp.md`

### Fase 2 — Estrutura dual-era

2. **Criar adapter de protocolo**
   - `backend/src/mcp-server/subscriptions/protocol-adapter.ts`
   - Interface comum: `subscribe(sessionId, uri)`, `unsubscribe(sessionId, uri)`, `notify(uri)`
   - Implementação LegacyProtocolAdapter: usa `sendResourceUpdated`
   - Implementação ModernProtocolAdapter (stub): será preenchida quando SDK v2 sair

3. **Atualizar SubscriptionManager**
   - Armazenar `protocolVersion` por session
   - Roteamento: se session usar modern, chama ModernProtocolAdapter; senão, LegacyProtocolAdapter

4. **Atualizar capabilities negotiation**
   - No `initialize`, detectar `protocolVersion` do cliente
   - Se `2026-07-28` ou superior → anunciar `resourceSubscriptions: true`
   - Se `2025-03-26` → anunciar `resources.subscribe: true` (comportamento atual)

### Fase 3 — Preparação para SDK v2

5. **Monitorar lançamento do SDK v2**
   - Adicionar script/check em CI quando nova versão for publicada
   - Quando disponível, implementar `ModernProtocolAdapter` com `subscriptions/listen`

6. **Manter backward compatibility**
   - `resources/subscribe` e `resources/unsubscribe` nunca serão removidos
   - Clientes antigos continuam funcionando sem alteração

### Fase 4 — Validação

7. **Testes de dual-era**
   - Simular cliente 2025: valida `resources/subscribe` + `sendResourceUpdated`
   - Simular cliente 2026 (stub): valida roteamento correto
   - Ambas as eras compartilham o mesmo EventBus

8. **Documentação**
   - Atualizar `docs/arquitetura-mcp.md` com estado real
   - Atualizar `README.md` com seção de compatibilidade
   - Atualizar `docs/protocolo-mcp.md` com examples de ambas eras

## 5. Critérios de aceite

- [ ] SDK v1.30.0 mapeado: confirmado que não há `subscriptions/listen`

- [ ] SubscriptionManager roteia por protocol version

- [ ] Testes dual-era passando
